# First Render deployment

The `render.yaml` Blueprint proposes four Starter web services in Singapore (Percy, coordinator, the runtime containing all eleven specialists, and the capability exchange), plus separate Basic 256 MB PostgreSQL instances for knowledge and private conversations. This is a paid configuration. Plan and review the exact resources/costs before applying it. Auto-sync and automatic deployment must remain off during the initial test.

The member-facing webpage remains on its current Sites hosting. This release does not enable Life Profile processing or put profiles into either database. A future Life Profile release needs a third separate database, its own key and dedicated service/delegation setup. Specialists never access member profiles.

## Order of operations

1. Plan the Blueprint from the pushed branch with auto-sync disabled; review and approve the resource plan. Supply the listed runtime values through Render secret settings. Do not reuse the database owner connection as any service runtime URL.
2. Apply the existing knowledge migrations 001–008 and separate conversation migration using migration credentials in a trusted operator shell on Render's private network. Check each migration release afterwards. Use `coordinator/database/runtime-role.sql`, `specialists/database/runtime-role.sql` and `persy/database/runtime-role.sql` to provision dedicated restricted runtime logins, reviewing public/inherited grants. Provision active coordinator/personal_ai identities and the coordinator's per-library research/retrieve grants for every specialist domain. The schema owner credentials must not appear in the service environments.
3. Provision one Ed25519 member gateway pair and one separate Ed25519 service exchange pair in secret managers. Only Sites holds the member PRIVATE key. Only the exchange holds the service PRIVATE key. Public keys are configured on verifier services. Generate independent high-entropy machine bearer secrets for Percy and the coordinator. Never reuse the provider API key as a machine credential.
4. Deploy the exchange with `EXCHANGE_MEMBER_PUBLIC_KEY`, `EXCHANGE_SIGNING_PRIVATE_KEY`, the two machine tokens and the verified Sites account subject. `POST /exchange/percy` only delegates authenticated, approved member research to the coordinator; `POST /exchange/coordinator` only delegates fixed-domain specialist dispatch for the coordinator machine. It does not grant profile access, arbitrary subject impersonation or administrative actions. The downstream runtimes independently enforce database grants, quotas and replay limits. Gate/limit ingress at the hosting layer as well; a valid machine credential is not permission for unrestricted public traffic.
5. Deploy specialists, then the coordinator, then Percy. Use their exact external HTTPS origins in the fixed service URL settings; never invent the origins before Render returns them. Match the exchange's service public key to both coordinator and specialist verifiers. The coordinator points to `/exchange/coordinator`; Percy points to `/exchange/percy`. Set the same corresponding machine token at each caller and its exchange verifier.
6. Configure evaluated structured-output-capable models and provider credentials separately on Percy/coordinator/specialists. Enforce provider spend limits. Ingest approved source excerpts; empty libraries produce honest evidence gaps, not researched findings.
7. Set Sites secrets `PERCY_SERVICE_URL`, `PERCY_GATEWAY_PRIVATE_KEY` and `PERCY_ALLOWED_USER_ID`. The allowed account subject must equal `EXCHANGE_ALLOWED_MEMBER_SUBJECT`. Preserve existing Sites access settings. The website's gateway admits only this one live-test account.
8. Test authenticated privacy reads, explicit model consent, an actual chat reply, exact research proposal review/approval, coordinator dispatch and findings/gaps. Check all eleven domain capabilities and service grants. Then test outages, account isolation, limits and history deletion. A `/health/live` response is only liveness, never proof that this chain works.

## Validation so far

The exchange has automated HTTP/signature tests for valid owner-bound research, all eleven domain dispatch tokens, cross-machine rejection, incorrect member scopes/subjects, arbitrary claim/target rejection and request size limits. Website tests cover owner-bound capabilities, no automatic research dispatch, explicit consent, service failures, unsafe text and existing social interactions. These are synthetic tests, not live model evaluation or proof of deployed availability.
